## What is a Database

A database is an organized collection of digital data stored and accessed from a computer system. It is usually managed by a Database Management System (DBMS).

### Relational Database

A relational database is a type of database that organizes data into predefined structures consisting of rows and columns, where relationships are established using unique identifiers called keys. They enforce strict, fixed blueprints known as schemas, and rely heavily on Structured Query Language to manage, alter, and retrieve information. 

## What is Structured Query Language (SQL)

Structured Query Language (SQL) is a language used to talk to many relational databases, including MySQL and PostgreSQL among many others. These systems share the same core SQL ideas, but each has its own dialect with small differences in syntax and features. 

## Primary and Foreign Keys

Primary and Foreign keys are foundational tools used to uniquely identify records and establish enforced links between different tables. They are used to enforce data integrity and make sure no data gets mixed up or lost. 

### Primary Key

A primary key uniquely identifies every row in its own table. It must be completely unique, and duplicates are not allowed. They cannot be NULL, and every row must have a valid value. 

A table can only have a single primary key which must contain unique values for each row. A table can have one primary key column, or it can have more than one that form a longer ID together, which is known as a **composite primary key**.

Here is a simple `users` table where `id` is the primary key. Each row is uniquely identified by that single column:

| id | name  | email             |
|----|-------|-------------------|
| 1  | Alice | alice@example.com |
| 2  | Bob   | bob@example.com   |
| 3  | Cara  | cara@example.com  |

Here is an `enrollments` table with a composite primary key on `(student_id, course_id)`. Neither column alone needs to be unique, but the pair must be:

| student_id | course_id | enrolled_on |
|------------|-----------|-------------|
| 1          | 101       | 2024-01-10  |
| 1          | 102       | 2024-01-12  |
| 2          | 101       | 2024-01-15  |

In this example, student `1` can enroll in multiple courses, and course `101` can have multiple students, but the same student cannot enroll in the same course twice.

So why use a composite primary key here? Students and courses have a **many-to-many** relationship: one student can take many courses, and one course can have many students. That relationship does not live cleanly inside `users` or `courses` alone. If you stuffed course IDs into each user row, or student IDs into each course row, the data would be awkward to update, easy to duplicate, and hard to query.

Instead, we use a middle table (often called a **junction table**) like `enrollments`. Each row means "this student is in this course." A composite primary key on `(student_id, course_id)` fits that idea well: the enrollment's identity *is* that pair, so the same student cannot be enrolled in the same course twice. In a real schema, `student_id` and `course_id` are usually foreign keys as well, pointing at `users.id` and `courses.id`.

You could also give `enrollments` its own single `id` primary key and add a separate unique constraint on `(student_id, course_id)`. That works too. The composite primary key is useful when the combination of columns is the natural unique identity of the row. 

### Foreign Key

A foreign key is used to link a row in one table to a matching row in another table. It can contain duplicate values, as many rows can link to the same target. It can be NULL if the relationship is optional for that specific record. A table can also have multiple foreign keys pointing to different tables. Foreign keys are usually references to a primary key (or unique key) from another table.

For example, a `courses` table might look like this:

| id  | title           |
|-----|-----------------|
| 101 | Intro to SQL    |
| 102 | Data Modeling   |
| 103 | Database Design |

An `assignments` table can store which course each assignment belongs to by using a foreign key. Here, `course_id` references `courses.id`:

| id | course_id | title              |
|----|-----------|--------------------|
| 1  | 101       | Select Basics      |
| 2  | 101       | Joins Practice     |
| 3  | 102       | ER Diagram Draft   |

Row one and two both belong to Intro to SQL (course `101`), and row three belongs to Data Modeling (course `102`). Multiple assignments can point at the same course, but the database will reject an assignment if `course_id` does not exist in `courses`, which keeps the relationship valid. This is a **one-to-many** relationship: one course can have many assignments, but each assignment belongs to one course.

## What is a Schema

A schema is the official blueprint, skeleton, or structural map that defines how data is organized. It tells the database exactly how tables, columns, data types, and relationships are structured before any data is entered. 

### Tables

Think of these as buckets holding your data: `users`, `courses`, `enrollments`, `assignments`. Tables have columns and rows, and it is a strong best practice to add a primary key to each table. 

### Columns and Data Types

This defines what kind of data is allowed in each column. For example, a `birth_date` column should only contain a `DATE`, while a `price` column would contain a `DECIMAL`.

### Constraints

These are rules of behavior. They specify which columns are primary keys, which are foreign keys, which cannot be left blank (NULL), and which must be unique, like `email`. 

### Relationships

Relationships define how tables connect to one another. For example, an `assignments` table may be linked to a `courses` table, or an `enrollments` table may connect `users` and `courses`. 

There are a few different kinds of relationships worth noting:

- **One-to-many:** One course, many assignments
- **Many-to-many:** Many students, many courses
- **One-to-one:** One user, one profile

## What is CRUD

CRUD is an acronym that stands for CREATE, READ, UPDATE, and DELETE. These are the four fundamental operations required to manage persistent data within almost any database or software application. Together, they form a concept of how software interacts with the database.

### CREATE

Adds new data or records to the database. 

**Example:** Posting a new tweet.

### READ

Retrieves or views existing data without changing it.

**Example:** Scrolling your timeline to read tweets.

### UPDATE

Modifies or edits existing data.

**Example:** Editing a typo in your tweet.

### DELETE

Removes existing data. The intent of DELETE is to get rid of a record, but applications do not always destroy it in the database.

**Example:** Deleting a tweet. 
**Note:** Twitter/X may not actually erase your tweet. It might instead mark it as unpublished and hide it, which is often called a soft delete. Whether a delete is permanent depends on how the app is architected.

## What is REST

Representational State Transfer (REST) is an architectural style for designing APIs around resources and standard HTTP methods. In practice, many REST APIs map roughly onto CRUD so a client (like a browser or mobile app) can talk to a server over the network. That mapping is a useful simplification, not the full definition of REST.

A common simplified mapping between CRUD, REST methods, and SQL statements looks like this:

| CRUD   | REST        | SQL    |
|--------|-------------|--------|
| Create | POST        | INSERT |
| Read   | GET         | SELECT |
| Update | PUT / PATCH | UPDATE |
| Delete | DELETE      | DELETE |

For updates, `PUT` often replaces a whole resource, while `PATCH` updates only some fields.

## Object-Relational Mapping (ORM)

An Object-Relational Mapping (ORM) is a software tool (sometimes library) that allows developers to interact with a relational database using their preferred programming language, like Python or JavaScript to name a few, instead of writing raw SQL queries. 

It acts as a translation layer between two different programming worlds: 

1. The Object-Oriented world: backend code organized into objects, arrays, and classes. 
2. The relational world: your database schema, organized into strict tables, rows, and columns.

Without an ORM, you would have to write raw SQL like this:

```python
cursor.execute("SELECT * FROM users WHERE name = 'Alice' AND status = 'active' LIMIT 1")
user = cursor.fetchone()

cursor.execute("UPDATE users SET email = 'alice@newemail.com' WHERE id = %s", (user['id'],))
```

But using an ORM like Django ORM, you can instead write this like below: 

```python
user = User.objects.filter(name='Alice', status='active').first()
user.email = 'alice@newemail.com'
user.save()
```

As you can see, using an ORM allows us to interact with a SQL database without writing a single line of SQL by yourself. This comes with a number of advantages and disadvantages. 

### ORM Advantages

- Faster development speed due to fewer lines of code
- Database agnostic, allowing you to switch to a different database (though this can still be painful)
- Built-in security such as parametrized queries
- Code autofill thanks to your code editor understanding your code objects and autocompleting your lines

### ORM Disadvantages

- The "black box" performance tax is the idea that an ORM may generate bloated inefficient queries. This is especially true for complex reports or massive joins. In some cases, raw SQL is more efficient.
- The learning curve is higher because you need to learn specific syntax associated with each ORM on top of the database work. 

## Not Only SQL (NoSQL)

Not Only SQL databases are a broad category of database management systems that manage data which does not fit neatly into the rigid, tabular structure of a traditional relational database. While all relational databases require a strict schema before adding data, NoSQL databases are non-relational, highly flexible, and some are built to scale horizontally across thousands of servers. There are four distinct structural models depending on the data they handle:

### Document Databases

These store data in documents, often (but not always) using `JSON` format. Every document can have a completely different structure, allowing you to add/remove data on the fly. 

**Usage:** User Profiles, Content Management Systems (blogs, e-commerce product catalogues, etc), and rapid software prototyping.

**Examples:** MongoDB, CouchDB, Amazon DynamoDB

### Key-Value Stores

This is the simplest model. It acts like a massive dictionary where every item is saved as a pair: a unique Key (identifier), and a Value (the data block).

**Usage:** High-speed caching, user session data (keeping a user logged in), real-time gaming leaderboards. 

**Examples:** Redis, Valkey, Amazon DynamoDB

### Wide-Column Stores

These store data in massive column families instead of rows. This allows the database to scan billions of rows across multiple distributed servers quickly, so long as you are looking at specific columns. 

**Usage:** Massive data analytics, IoT sensor logging, time-series data like financial market tracking.

**Examples:** Apache Cassandra, ScyllaDB, Google Bigtable

### Graph Databases

These focus entirely on the relationships between data points. They map data as `Nodes` (entities like people or products) and `Edges` (the connection between them).

**Usage:** Social networks, fraud detection networks, recommendation algorithms, etc.

**Examples:** Neo4j, Amazon Neptune
